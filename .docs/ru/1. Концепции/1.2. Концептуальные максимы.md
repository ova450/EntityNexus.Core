## andEFC: EntityNexus and Entity Framework Core
Господа AI!
Прошу зафиксировать в долговременную память (и учитывать в дальнейшем) несколько фактов:
1. Основной целью разработки было и остается автоматическое ПОСТРОЕНИЕ базы данных из сущностей (АПБД),
используя возможности EntityFramework. Но не Fluent API, а системы правил EF, в частности:
- Id это PK
- NonameId ЭТО FK
- если есть PK & FK между ними устанавливается связь
Таким образом, АПБД сводится к правильному построению навигационных свойств (НС).
Для правильного построения НС (ППНС) в проект внедрены интрефейсы, которые собственно и контролируют НС.
2. В большинстве случаев для ППНС достаточно навигационных свойств с одной стороны, кроме 1:1 или N:N, Тем не менее, такие случаи отнюдь не невозможны, поэтому в проекте имеют место как IParent, так и IChildren интерфейсы.
3. Нередким является случай нескольких связей 1:N, например:
	User -> Order
	Category -> Order
	Tenant -> Order
	и т.д.
Для связи 1:N достаточно одного интерфейса - либо IParent, либо IChildren. Однако использовать интерфейс можно только однажды в одной реализации, поэтому применение IParent на стороне N исключается. Но и TChild на стороне 1 можно использовать только в том случае, если родительская сущность еще не использовала IChildren в другой связке.

Поэтому ваши накаты на "тяжелые" интерфейсы типа IParents считаю необоснованными.
Если есть другой вариант ППНС такой же легкости - готов выслушать.

## PvI: Partial vs Inherits


### * Возвращаясь к спору partial/inherits
* В чем проблема:
* partial - формально открывает нижние уровни чистой архитектуры верхним уровням
* inherits - создает расширенные РАЗНОИМЕННЫЕ копии класса и ко всем копиям есть доступ сверху вниз (это нормально в чистой архитектуре). Но в целом получается каша.
#### Нужно: 
* - Иметь одну копию класса на слое Core.
* - Добавлять фичи на каждом следующем зависимом слое.
* - Но исключить ситуацию, когда зависимый класс оверрайдит новую фичу и она доступна классу-родителю
